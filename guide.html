01

Processes

A process is an async generator run by spawn. In a real app you name its three types with Proc<State, Message, Args>: what it yields, what messages it accepts, and what it is started with.


import { spawn } from '@nonchalant/core'
import type { Cast, Proc } from '@nonchalant/core'

type Msg = Cast<{ type: 'add'; by: number }> | Cast<{ type: 'reset' }>

const counter: Proc<number, Msg, { start: number }> = async function* (self, { start }) {
  let n = start
  yield n
  for await (const msg of self) {
    switch (msg.type) {
      case 'add':
        n += msg.by
        break
      case 'reset':
        n = start
        break
    }
    yield n
  }
}

const c = spawn(counter, { start: 10 }, { initial: 10 })
c.cast({ type: 'add', by: 5 })

Messages are a union of object types told apart by their type field, and the loop handles them with a switch, one case per message. The loop body plays the part other libraries give to a reducer, except that it can also await, keep private variables, and yield more than once.

State is updated immutably: reassign the let with a new object, spreading in whatever didn't change, as in s = { ...s, total }. The parts that didn't change stay identical, which is what makes updates cheap (section 06 explains why).

The third argument to spawn holds options. Besides initial, the most useful is restart: 'on-crash', which reruns the generator from its arguments if it throws.

02

Messages: cast and call

There are two kinds of message. A cast is one-way: the sender doesn't wait. A call expects an answer: the sender gets a promise, and the process answers by calling msg.reply. The message type says which is which:


type Item = { id: string; name: string; price: number }
type Cart = { items: Item[]; total: number }
type CartMsg =
  | Cast<{ type: 'add'; item: Item }>
  | Cast<{ type: 'clear' }>
  | Call<{ type: 'checkout' }, { ok: boolean; charged: number }>

const cart: Proc<Cart, CartMsg, void> = async function* (self) {
  let s: Cart = { items: [], total: 0 }
  yield s
  for await (const msg of self) {
    switch (msg.type) {
      case 'add':
        s = { items: [...s.items, msg.item], total: s.total + msg.item.price }
        break
      case 'clear':
        s = { items: [], total: 0 }
        break
      case 'checkout':
        msg.reply({ ok: s.items.length > 0, charged: s.total })
        continue                          // answered, state unchanged: no yield
    }
    yield s
  }
}

Inside the loop, break leaves the switch and reaches the yield at the bottom. continue skips it, which is how a process says "nothing changed, publish nothing". From the outside:


const shop = spawn(cart, undefined, { initial: { items: [], total: 0 } })
shop.cast({ type: 'add', item: boots })
const receipt = await shop.call({ type: 'checkout' })   // typed: { ok: boolean; charged: number }

TypeScript routes each message: cast refuses a call, call refuses a cast, and the reply is typed. If the process crashes, finishes, or is disposed before it answers, the promise rejects instead of hanging.

Every handle also has three status reads: pending (the process is working toward its next yield), stale (the value survived a crash or a lost connection), and error (the last failure). They are reads like any other, so a view shows them the same way it shows state.

03

Input, in order

Messages wait in the mailbox and are handled one at a time. While a process is busy, awaiting a request for example, new messages queue behind it instead of interleaving with it. That removes a whole class of race: a double-clicked submit is handled twice, in order, never both at once.

When only the newest input matters, loop over self.latest() instead of self. Each time the loop asks for the next message, it gets the most recent one, and anything older is dropped. That is a typeahead with no debounce timer:


for await (const { q } of self.latest()) {             // skip to the newest query
  yield { q, results, pending: true }
  try {
    results = await search(q, { signal: self.signal })  // aborted if the process is disposed
    yield { q, results, pending: false }
  } catch {
    /* aborted or failed: keep listening */
  }
}

self.signal is an AbortSignal that fires when the process is disposed or crashes. Pass it to every fetch, and work that belongs to a process that no longer exists is cancelled. The typeahead demo on the overview runs this loop.

04

Lifetime and ownership

A process ends when its generator returns, when it throws (unless it is set to restart), or when it is disposed:


c[Symbol.dispose]()               // start teardown now
await c[Symbol.asyncDispose]()    // or: start it, and wait until every finally block has run

Disposal closes the mailbox, aborts self.signal, and runs the generator's finally blocks. Anything a process spawns belongs to it and is disposed with it, so cleanup follows structure: dispose a page and everything the page started goes too.

One rule to remember. A process owns what it spawns during the synchronous part of each step. Spawn children before your first await; a spawn after it runs unowned.

Processes are cheap enough to be short-lived. This demo starts one per drag: it begins on pointer-down, yields a position for each move, and is disposed on pointer-up, taking its subscriptions with it.

05

Views and bindings

Views are plain function calls. @nonchalant/dom/tags exports one function per HTML element, called as div(attributes, ...children), and h('my-element', attributes, ...children) covers any other tag. Nothing is parsed from strings, so text from your data can never turn into markup.

A component is an ordinary function that takes the processes it needs and returns a tree:


function Summary(shop: Process<Cart, CartMsg>): VNode {
  return div({},
    span({}, () => `${shop().items.length} items, $${shop().total}`),   // a text binding
    button({
      disabled: () => shop().items.length === 0,                       // an attribute binding
      onclick: () => shop.cast({ type: 'clear' }),
    }, 'clear'),
    ul({}, () => shop().items.map((item) => li({ key: item.id }, item.name))))  // a keyed list
}

The function runs once. Each function inside the tree is a binding, whether it sits in a child position or an attribute, and so is a process placed directly in the tree. A binding runs again whenever something it read changes, and it updates only its own spot on the page. (onclick is different: it's an event handler, called when the event fires.)

Structure changes happen inside bindings too. A binding that returns elements is a region, which the renderer patches in place. A binding that returns an array of elements with keys is a keyed list: rows are matched by key, and only the rows that were added, removed, or moved touch the DOM.

Outside a view, two functions subscribe in the same way:


const itemCount = derive(() => shop().items.length)
const stop = effect(() => {
  document.title = `Cart (${itemCount()})`
})

derive computes a value from other processes and can be read like a process itself; it notifies its readers only when its result actually changes. effect runs a side effect now, and again whenever what it read changes. It is for pushing state to things outside Nonchalant, such as the document title, and it returns a function that stops it.

Reads don't subscribe by accident. Reading shop() inside a binding, derive, or effect subscribes to what was read. Anywhere else, such as an event handler, it returns the current value and subscribes to nothing.
06

How updates stay small

Libraries usually make you choose between plain data and precise updates. Nonchalant gives you both.

With plain immutable data (React, Redux), state is easy to reason about, but a change re-runs whole components, and you memoize to win back the cost. With reactive containers (signals, observable stores), updates are precise, but your state is no longer plain data. Nonchalant keeps plain data and makes updates precise in three steps:

  1. Each yield is diffed. The new state is compared with the previous one, producing a list of changed paths. Immutable updates keep unchanged parts identical, so the comparison skips them without looking inside. Its cost follows the size of the change, not the size of the state.
  2. Each binding records what it reads. While a binding runs, its reads go through a short-lived proxy that notes which paths it touched, such as total or items[3].done.
  3. Only matching bindings run. A binding runs again only if the diff includes a path it read.

s = { ...s, total: s.total + item.price }   // an ordinary immutable update
yield s                                     // the diff: total changed

// () => cart().total              runs again
// () => cart().items[3].done      does not

There is no compiler and no dependency list. What it asks of you is the update style: reassign with let and spread. Mutating an object in place hides the change from the diff, and deep-cloning everything makes every part look changed.

07

Sharing state by name

A process that one component uses can be spawned right where it's needed. State that several parts of an app need, or that is expensive to create, goes in a registry:


import { define, registry } from '@nonchalant/core'

const app = registry({
  cart: define(cart, { initial: { items: [], total: 0 } }),
  product: define(product, { evict: 60_000 }),     // dropped a minute after its last reader leaves
})

const mine = app.lookup('cart')                    // the cart, wherever it is asked for
const p1 = app.lookup('product', { id: 'boots' })  // starts the process
const p2 = app.lookup('product', { id: 'boots' })  // the same process as p1

lookup(name, args) is get-or-spawn. The first lookup starts the process; later lookups with the same name and arguments return the same one. That one mechanism does three jobs:

  • Dependency injection. A component asks for what it needs by name, with no provider tree and no prop drilling.
  • A query cache. The arguments are the cache key, every reader shares one entry, and evict drops the entry a set time after its last reader leaves.
  • Remote addressing. A connection to a worker or a server has the same lookup, so the same call can reach a process somewhere else. That's the next page.

08

Shorter forms

Everything so far is the generator. Two common cases have a shorter way to write one. Each produces an ordinary process, so everything on this site treats it the same way:

ShorthandWhat it stands for
cell(initial)A process whose messages are its next values: widget state, the useState case.
reducer(init, reduce)The loop, switch, and yield process, written as a function from state and message to the next state.

Here is a counter written with reducer. Returning the same state means nothing changed, so nothing is yielded:


import { reducer } from '@nonchalant/core'
import type { Call, Cast } from '@nonchalant/core'

type Msg = Cast<{ type: 'add'; by: number }> | Call<{ type: 'get' }, number>

function count(n: number, msg: Msg): number {
  switch (msg.type) {
    case 'add':
      return n + msg.by
    case 'get':
      msg.reply(n)
      return n                    // the same state: nothing is yielded
  }
}
const counter = reducer(() => 0, count)

A reducer is synchronous and keeps no private state. Once a process needs to await, yield more than once for a message, or clean up in finally, write the generator instead; its messages and its callers stay the same.

09

Seeing inside

A process keeps its state inside a suspended generator, where browser devtools can't see it. @nonchalant/inspect can. It records every spawn, message, reply, yield, crash, and exit, and shows the live process tree, a timeline of events, and the state of any process at any recorded moment.


import { mountInspector } from '@nonchalant/inspect'

const panel = mountInspector(document.getElementById('inspector')!)   // before the processes it should see

Yields are stored as the same patches the diff produces, so stepping back in time replays them instead of keeping a copy of every state. To try it, add ?inspect to the TodoMVC or agent example.

Quick reference

A handle, from the outside:

MemberWhat it does
p()Reads the latest value. Inside a binding, derive, or effect, it also subscribes to the paths read.
p.cast(msg)Sends a one-way message.
p.call(msg)Sends a request and returns a promise of the typed reply. Rejects if the process crashes, finishes, or is disposed first.
p.pending, p.stale, p.errorWorking toward the next yield; the value survived a failure; the last failure.
for await (const v of p)Iterates over values. A slow reader gets the newest value, never a backlog.
p[Symbol.dispose]()Starts teardown now.
await p[Symbol.asyncDispose]()Starts teardown and waits for it, children included, to finish.

And self, from the inside:

MemberWhat it does
for await (const msg of self)Takes queued messages in order.
self.latest()The same loop, skipping to the newest message each time.
self.signalAn AbortSignal that fires on disposal or a crash.
self.cast(msg)Sends a message to the process's own mailbox, so background work can report back.
