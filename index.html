Nonchalant

One primitive. A process owns its state, takes messages in order, publishes snapshots, and does not care which side of the wire it runs on.

Async generators, plain let state Views run once Fine-grained updates, no compiler Experimental — not yet on npm
01

The idea

A generator already has the three things a piece of application state needs: local variables to hold it, a loop to take input in order, and an end. Nonchalant runs that generator and gives you a handle to it.

You write a process as an async generator. spawn runs it and hands back a typed handle you can read, send to, ask, iterate, and dispose. State is ordinary let variables; input is for await; output is yield. There is no store, no reducer registration, no dependency array.


import { spawn } from '@nonchalant/core'
import type { Self } from '@nonchalant/core'
import { mount } from '@nonchalant/dom'
import { button, div, span } from '@nonchalant/dom/tags'

const counter = spawn(async function* (self: Self<number>) {
  let n = 0                          // this is the state
  yield n
  for await (const d of self) {      // this is the input
    n += d
    yield n                          // this is the output
  }
}, undefined, { initial: 0 })

mount(document.getElementById('app')!, div({},
  button({ onclick: () => counter.send(-1) }, '−'),
  span({}, counter),                 // a live binding
  button({ onclick: () => counter.send(1) }, '+')))

That same unit scales up without changing shape. A widget's state is a process. Shared application state is a process, reached by name. A cached query is a process with an idle timeout. A process on a server is the same process, reached through a transport instead of a function call.

What it is not. Not a React-compatible component model, not an Erlang runtime, not a complete query client. It is an experiment in how far one primitive goes — and it is honest about the edges, which are written down rather than glossed.
02

Get it

The packages are not published yet — the npm scope claim and first release are still to come. For now it is a clone-and-explore library:

git clone https://github.com/twfarland/nonchalant
cd nonchalant
pnpm install

pnpm dev     # this site at /, the example gallery at /examples/
pnpm test    # the whole suite, including the perf, size, and DOM-write budgets
pnpm check   # strict TypeScript across packages, examples, and this site

@nonchalant/core

The process runtime, the reactive graph, the structural diff, and the registry. Zero dependencies, never touches the DOM.

@nonchalant/dom

Tag constructors and the DOM sink. Builds nodes with createElement only — no string is ever parsed as markup.

@nonchalant/wire

The eight-op protocol, its codec, and transports. Isomorphic and DOM-free, with cross-language conformance vectors.

@nonchalant/durable

A wrapper that writes a process down: the message journal, the effect journal, and a six-method store contract.

@nonchalant/host

The Node WebSocket host: origin policy, handshake authorization, per-connection scoping, and connection limits.

03

The primitive

One noun with two faces. Process is what a holder of the running thing can do; Self is what the generator itself receives.

From the outsideWhat it does
p()Read the latest value, synchronously. Inside a binding, effect, or derive this also subscribes — by path. Anywhere else it is just a read.
p.send(msg)Fire-and-forget. Exists only if the message type has plain messages.
p.ask(msg)Request/response, typed. Exists only if the message type has Call messages. Rejects if the process crashes, ends, or is disposed.
p.pending / p.stale / p.errorLifecycle as ordinary reads. Loading and failure states are values, not a separate mechanism.
for await (v of p)A lossy latest-value stream. You always get the newest, never a backlog.
p[Symbol.dispose]()Teardown: the mailbox closes, the signal aborts, finalizers run, owned children die with it.
From the insideWhat it does
for await (msg of self)The mailbox, in order. Messages queue while you are busy — sequential handling is the default, so a double-submit queues instead of racing.
self.latest()Skip to the newest message and drop the rest. What a typeahead wants.
self.signalAn AbortSignal that fires on dispose or crash. Thread it into every fetch.
self.send(msg)Post to your own mailbox — the actor self-send, for background work reporting back.

A message that expects an answer is a Call, and the compiler keeps the two straight: it refuses to send a call or ask a cast.


type CartMsg =
  | { type: 'add'; item: Item }                                   // a cast
  | Call<{ type: 'checkout' }, { ok: boolean; charged: number }>  // a call

cart.send({ type: 'add', item })                 // fine
const res = await cart.ask({ type: 'checkout' }) // res is typed; a crash rejects it

05

Why the updates stay small

You write ordinary immutable updates. Every yield is diffed structurally against the previous snapshot, and a reader wakes only if a path it actually read is in the diff.


s = { ...s, total: s.total + item.price }   // an ordinary immutable update
yield s                                     // diffed → only /total readers wake;
                                            // a binding on items[3].done sleeps through it

Nothing declares its dependencies. Reads inside a tracked context go through a short-lived recording proxy, so the set of paths a binding depends on is observed rather than annotated — which is why there are no dependency arrays, no memos, and no re-render tax to defend against. Views run once and never rebuild; structural change is expressed as keyed lists or swapped regions.

06

Over the wire

lookup(name, args) is one operation doing three jobs: dependency injection, query caching, and — once a transport is involved — remote addressing. A transport is only send plus subscribe over something ordered and reliable, which a socket, a worker port, and a tab-to-tab bus all are. So the choice of where the state lives is one line, and it is the only line that changes:


const shop = registry({ cart: define(cart) })                        // this tab
const shop = connect<Shop>(portTransport(new Worker(url)))           // another thread
const shop = connect<Shop>(broadcastChannelTransport('shop'))        // another tab
const shop = connect<Shop>(webSocketTransport('wss://…'))            // another machine

Everything downstream of that line is identical in all four cases, and it is identical because it is the same code, not because four backends were made to look alike:

The same at every distanceWhy
The process itselfIt never learns where it runs. examples/shared-cart ships one definition the tab and the Node host both execute; examples/worker runs one definition on either side of a thread boundary, switchable while it runs.
send and askA cast is one op on the wire, a call is a correlated pair. The compiler still refuses to send a call or ask a cast.
Fine-grained updatesA remote process is a local process that applies patches, so a binding on /items/3/done sleeps through a change to /total whether the yield came from this thread or a datacentre.
Loading and failurepending, stale, error are ordinary reads. A dead host reads exactly like a crashed local process: last value intact, stale: true.
TeardownSymbol.dispose releases the watch, and the host reclaims the process when the last watcher leaves.

What crosses is a patch of plain data — never markup, never code. That is what keeps rendering and local interaction on the client, keeps the payload proportional to the change rather than the page, and lets any language implement the host half against the conformance vectors in packages/wire/spec/. Reconnecting is not a special case either: the client looks its names up again and the first yield after any lookup is a full snapshot, which diffs against what it kept — so readers of unchanged paths sleep straight through the outage.

The distance is not free, and the library does not pretend otherwise. State has to be JSON-shaped; a Date or a class instance is an atomic leaf that will not survive a remote lookup. Calls can fail and arrive late. The published schema is a whitelist of names, not an identity check — authorization belongs at the host and inside the processes. Those costs are real; what the wire removes is the second implementation of your application state.

These demos need a terminal, not a server you have to deploy. The chat room and the shared cart run against a local Node host — pnpm chat-server or pnpm cart-server, then open the page from pnpm dev. The shared-cart page also runs standalone with its state in the tab: one commented line swaps between the two. Before putting a host on the internet, read Hosting safely — origin policy, authorization, per-connection scoping, and the limits that are not on by default.

Two of them need no server at all. multi-tab elects one tab as the host over a BroadcastChannel and moves the job when you close it — open it twice. worker puts the grinder from the demo above on a thread, with a switch that moves it back and forth while it runs: the numbers are identical either way, and only the frame meter can tell.

07

The same primitive on the server

Nothing in the core package is about the browser. A process is a mailbox, a generator, and a supervisor — the shape an actor has had since Erlang. What follows is that same primitive at three depths: state that lives on a server, state that survives the server restarting, and state that decides what to do next.

One: a room on a server

The chat example is the plainest version. A room is a process that folds posts into a capped history — no sockets in it, no sessions, no idea it is a chat server:


export const room: Proc<RoomState, RoomMsg, { name: string }> = async function* (self) {
  let lines: ChatLine[] = []
  let nextId = 1
  yield { lines }
  for await (const msg of self) {
    lines = [...lines.slice(-49), { id: nextId++, from: msg.from, text: msg.text }]
    yield { lines }
  }
}

Hosting it is one line, and reaching it from a tab is the lookup you already know. The name is the address: same name, same room, for everyone.


// the server
const host = await serve({ room: define(room, { evict: 3_600_000 }) }, { port: 4322 })

// a tab
const conn = connect<ChatSchema>(webSocketTransport('ws://127.0.0.1:4322/'))
const lobby = conn.lookup('room', { name: 'lobby' })   // get-or-spawn, on the server
Architecture — tabs, one host, a process per room 
flowchart LR
  T1["tab A"] -- "lookup room lobby" --> H
  T2["tab B"] -- "lookup room lobby" --> H
  T3["tab C"] -- "lookup room dev" --> H
  H["the host: one wire session per socket"] --> REG["registry: a name plus its args is the address"]
  REG --> P1[["room lobby"]]
  REG --> P2[["room dev"]]
  P1 -- "yield, diffed to a patch" --> H
  H -- "patch" --> T1
  H -- "patch" --> T2

The registry is the room lifecycle: a room is spawned by the first lookup, shared by every later one, and evicted an hour after the last tab leaves. A suspended generator is kilobytes, so one node holds thousands of them. Kill the server mid-conversation and the tabs keep their last value with stale: true until the transport reconnects and the re-lookup answers with a full snapshot.

Run it in a terminal, not a deployment. pnpm chat-server, then open /examples/chat/ in a few tabs. Before putting a host on the internet, read Hosting safely — origin policy, authorization, per-connection scoping, and the limits that are not on by default.

Two: state that outlives the process

A chat room can afford to be forgotten. An order, a job, a long-running task cannot. @nonchalant/durable wraps a process and writes it down; what comes back out is an ordinary Proc, so it still goes in a registry, over the wire, and under a view.


const orders = registry({
  order: define(durable(order, { store, key: (args) => args.id })),
})

The transaction boundary is one message. It is journaled before it is handled; each effect inside d.step is journaled as it completes; and when the process asks for its next message, the state it produced and the cursor past the handled one are committed together. Crash in between and the message is delivered again with its finished effects already answered — the generator re-runs, the effects do not.

Architecture — what gets written down, and when 
sequenceDiagram
  participant C as caller
  participant D as durable wrapper
  participant S as store (a port)
  participant P as your process
  C->>D: send, or ask with a callId
  D->>S: append(message)
  D->>P: deliver
  P->>D: step("charge")
  D->>S: putStep(result)
  P->>D: yield state
  P->>D: ask for the next message
  D->>S: commit(state, cursor) - together, or not at all
  Note over D,S: a crash before that commit delivers the message again
  Note over D,S: recorded steps answer from the journal instead of running

Calls are durable too, which is what makes a durable process worth calling. An ask into one carries an idempotency key; the answer is recorded under it, and a retry is answered from the record. d.call derives that key from the caller, the message it is handling, and the name, so a replay asks with the same one:


const receipt = await d.call('reserve', (callId) =>
  vault.ask({ type: 'reserve', amount: 100, callId }))

So a repeated call does no work twice; two callers on one id wait on one answer; a caller that died after the answer landed retries and gets that answer back; and a callee that answered but died before acknowledging does not handle the message again.

The store is a port — eight methods, no base class, no registration, and the wrapper knows nothing else about storage. This repo ships the in-memory adapter only: it is the reference implementation and the rig the crash-consistency property runs against. An adapter for a real store belongs in the repo that owns that driver.

How durable execution is usually doneThe trade
Temporal replays workflow code against an event historyExact replay — at the price of code that must stay deterministic, with every effect behind an activity.
DBOS and Restate journal each step of ordinary codeOrdinary code — at the price of at-least-once on the step that was in flight.
Here: journal the message, journal the steps, commit the snapshot with the cursorThe same trade as DBOS and Restate, plus the snapshot: recovery reads one state instead of replaying a history. Journaled steps are exactly-once; an effect in flight when the process died runs again.

What is deliberately absent: a worker fleet, a scheduler, a cron, a retry-policy language, and an execution console. A mailbox is also a single writer only while one node owns the name — several hosts activating the same id need a lease in the store, which is a distributed-systems problem no API removes.

What is at the edges

A backend eventually talks to something that fans out and something that hands out work. Both go behind a port, and the messaging demo has the two that matter with in-memory adapters. What is worth noticing is what happens on this side of them: a subscription is a process — subscribe on the way in, self.send each event, and let disposal be the unsubscribe — so an external stream becomes ordinary state that a view binds to. Look one up by topic and the registry becomes the subscription cache, one per topic however many readers there are.

A queue worker is a process too: reserve under a lease, handle, acknowledge, release on failure. Press kill in that demo while a worker holds a job — nothing acknowledges it, the lease expires, and the other worker picks it up with attempts one higher. At-least-once lives in the queue rather than in the worker, which is the same guarantee durable() gives inside a process, arriving from the other direction.

Three: a process that decides what to do next

An agent loop takes a question, calls out, looks at what came back, and yields as it goes. That is the same sentence as the one describing a todo list — so the agent below is not a second framework that happens to share a vocabulary. It is the primitive from section 03, wrapped in the durability just described, running on this page.

Agent stubbed model · ask about a process, patch, worker, durable · or "refund 20"
source

Tools are processes, so a tool call is ask(). A tool has state you can watch — the search tool counts its own calls — and it can be reached from anywhere, because reaching it is a registry lookup and a lookup does not care about distance.

It also means human-in-the-loop needs no mechanism. Say refund 20 to the demo: the approval tool receives the request and does not reply until you click. The agent's side is an ordinary await; the queue of waiting requests is ordinary state, which is why the buttons that answer it are an ordinary view.


for await (const msg of self) {
  if (msg.type === 'request') waiting = [...waiting, { ...msg, reply: msg.reply }]  // parked
  else { waiting[0]?.reply(msg.ok); waiting = waiting.slice(1) }                    // a person decided
  yield state()
}

Press kill it in the middle of a question: the process is disposed, the next lookup activates a new one, and it carries on from the journal instead of asking the model again.

Several agents

The patterns the agent frameworks name are, here, ordinary process code. The multi-agent demo runs all of them: a supervisor briefs a researcher, hands what comes back to a writer, and stops for a person before publishing.

The tests are the honest part. examples/agent/agent.test.ts and examples/multi-agent/multi-agent.test.ts drive every one of these with no DOM and no network — the model is an argument, the tools are processes, and a run reads as a transcript of yields — while packages/durable proves crash consistency as a property, running generated crash schedules and checking the workflow lands where the uninterrupted run landed.
