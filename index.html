Nonchalant

Write application state as async generators. The page updates only where the state changed, and the same process runs in a worker, another tab, or on your server.

A research project, not a product. Nothing is on npm, and the API and wire protocol may change without notice. Read it, run the demos, take the ideas, but don't ship it to production yet.

01

Why it exists

A typical web app manages its state with several different tools, each with its own rules.

Component state lives in hooks or signals. Shared state lives in a store. Server data lives in a query cache. Live updates need a socket layer that keeps a local copy in sync, and long-running backend jobs need a workflow engine. Each has its own API, its own lifecycle, and its own ways to fail, and moving a piece of state from one to another means rewriting it.

The same bugs turn up in all of them: two clicks racing each other, a callback reading a stale value, a dependency array missing an entry, a response arriving after the user has moved on, a component re-rendering because of a change it doesn't even display.

Nonchalant tries one primitive for all of it, and it's one JavaScript already has. An async generator can keep state in local variables, take input in order with for await, publish with yield, and clean up in finally. Nonchalant runs it as a process and handles the rest: delivering messages, updating the page, and carrying state across threads and networks.

02

A process in one minute

A process owns one piece of state and handles messages one at a time. Here is a counter:


import { spawn } from '@nonchalant/core'
import type { Self } from '@nonchalant/core'

async function* counter(self: Self<number>) {
  let n = 0                        // the state: an ordinary variable
  yield n                          // publish it
  for await (const d of self) {    // take each message, in order
    n += d
    yield n                        // publish the new state
  }
}

const count = spawn(counter, undefined, { initial: 0 })
count.cast(1)                      // send it a message
count()                            // read the latest state

spawn starts the generator and returns a handle. Its second argument is what the process is started with (this counter needs nothing), and initial is what a read returns before the first yield. Calling the handle, count(), reads the latest state. count.cast(1) puts a message in the process's mailbox. Messages are handled strictly in order, so three quick clicks always add three.

There is no store to configure and no reducer to register. The state is a let, the update logic is the loop body, and the process lives until its generator returns or you dispose it.

Putting it on the page

Views are built from tag functions and mounted once:


import { mount } from '@nonchalant/dom'
import { button, div, span } from '@nonchalant/dom/tags'

mount(document.getElementById('app')!, div({},
  button({ onclick: () => count.cast(-1) }, '−'),
  span({}, count),                                         // a binding: shows the count
  button({ onclick: () => count.cast(1) }, '+'),
  span({}, () => (count() % 2 === 0 ? ' even' : ' odd'))))  // so is a function

The view runs once and creates real DOM nodes. A process or a function placed in the tree is a binding: a live spot that updates itself when the state it read changes. Nothing else runs again. There is no re-render, so there are no dependency arrays, no memoization, and no stale closures to manage.

03

What's different

Each of these gets a full explanation later; the link under each one goes there.

Plain data, precise updates

State is ordinary immutable objects and arrays, not signals or observable stores. Each yield is compared with the previous one, and only the bindings that read a changed value run again. Editing one row of a long list writes to that row alone.

How updates stay small →

Input can't race

Each process handles one message at a time. A double-submitted form queues instead of colliding, a search box can skip straight to the newest query, and in-flight requests are cancelled when their process ends.

Input, in order →

Location doesn't matter

A process doesn't know where it runs. One line moves it into a Web Worker, another tab, or a server, and the code that reads it stays the same. Only small patches of data cross the connection, never HTML.

Run it anywhere →

One model, front to back

The same shape covers a toggle, shared app state, a cached query, a chat room on a server, an order that survives a crash, and an AI agent that waits for a person's approval. One library where you would otherwise assemble a stack.

Servers, workflows, and agents →

Tests without a browser

A process is a generator, so a test sends it messages and checks what it yields. Clocks and services are passed in as messages and arguments, so tests run without a DOM, a network, or real delays.

Testing →

Measured, not promised

The claims about update precision are assertions in CI: exact DOM-write counts for a game and a 1,000-row benchmark, a bound on diff time, and checks that nothing leaks after disposal.

05

Where it fits

Nonchalant borrows from projects you may already know:

If you knowYou'll recognize
Erlang/OTPProcesses with mailboxes, cast and call, processes addressed by name, and children that end with their parent.
Solid and signalsFine-grained updates with no virtual DOM. The propagation engine is a port of alien-signals.
CrankGenerators that keep their own state between updates.
TanStack QueryEntries cached by their arguments, shared by every reader, and dropped when idle.
Phoenix LiveViewState owned by a server and pushed to the browser, except as data patches rather than HTML.
Temporal, RestateWorkflows that survive a restart because what they did was written down.

What's new is putting all of these behind one primitive. A piece of state can grow from a widget into shared state, move to a server, and become a durable workflow without being rewritten, and the code that reads it doesn't change along the way.

What it isn't

  • Not React-compatible. Views are function calls such as div({}, …) rather than JSX, and there is no re-render to hook into.
  • Not an Erlang runtime. Processes are cooperative JavaScript: no preemption, no isolation, no supervision trees. A long loop still blocks its thread; move it to a worker.
  • No server-side rendering yet. A server holds processes and sends their state; the browser builds every DOM node.
06

Get started

Nothing is on npm yet. To try it, clone the repository:

git clone https://github.com/twfarland/nonchalant
cd nonchalant
pnpm install

pnpm dev     # this site at /, the example gallery at /examples/
pnpm test    # the whole suite, including the update-count budgets
pnpm check   # strict TypeScript across packages, examples, and this site

It is split into packages so an app takes only what it uses:

PackageWhat it gives you
@nonchalant/coreProcesses, the registry, and the reactive graph. No dependencies and no DOM, so it runs anywhere JavaScript does.
@nonchalant/domTag functions and the renderer. Text is never parsed as HTML.
@nonchalant/wireConnections to processes in a worker, another tab, or a server.
@nonchalant/durableProcesses that survive a crash or a restart, over a storage interface you can implement for your database.
@nonchalant/hostA Node WebSocket server for processes, with origin checks, authorization, and rate limits.
@nonchalant/inspectA panel that shows live processes, the messages between them, and their past states.
