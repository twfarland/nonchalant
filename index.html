Nonchalant

Build application state with processes that receive messages in order and publish snapshots. Run the same process in a browser, a worker, or on a server.

Async generators with plain let state Views execute once Targeted updates without a compiler Experimental, not yet on npm
01

The idea

Async generators are a practical fit for application state. Local variables hold the current value, a loop handles input in order, and the generator has a clear lifetime. Nonchalant runs the generator and returns a handle for working with it.

A process is an async generator. Call spawn to run it and get a typed handle that supports reads, messages, requests, iteration, and disposal. Use ordinary let variables for state, for await for input, and yield for output. You do not need to configure a store, register reducers, or maintain dependency arrays.


import { spawn } from '@nonchalant/core'
import type { Self } from '@nonchalant/core'
import { mount } from '@nonchalant/dom'
import { button, div, span } from '@nonchalant/dom/tags'

const counter = spawn(async function* (self: Self<number>) {
  let n = 0                          // this is the state
  yield n
  for await (const d of self) {      // this is the input
    n += d
    yield n                          // this is the output
  }
}, undefined, { initial: 0 })

mount(document.getElementById('app')!, div({},
  button({ onclick: () => counter.cast(-1) }, '−'),
  span({}, counter),                 // a live binding
  button({ onclick: () => counter.cast(1) }, '+')))

The model stays the same as an application grows. A process can manage one widget, shared state addressed by name, or a cached query with an idle timeout. Move it to a server and only the connection changes; callers still use the same process interface.

Scope. Nonchalant is not a React-compatible component model, an Erlang runtime, or a complete query client. It explores how much of an application can be built around one primitive, with its current limits documented alongside its features.

Get it

The packages have not been published to npm yet. Until the first release, clone the repository to try the library:

git clone https://github.com/twfarland/nonchalant
cd nonchalant
pnpm install

pnpm dev     # this site at /, the example gallery at /examples/
pnpm test    # the whole suite, including the perf, size, and DOM-write budgets
pnpm check   # strict TypeScript across packages, examples, and this site

@nonchalant/core

Process runtime, reactive graph, structural diffing, and registry. It has no dependencies and does not access the DOM.

@nonchalant/dom

Tag constructors and DOM output. Nodes are created with createElement; strings are never parsed as markup.

@nonchalant/wire

An eight-operation protocol, codec, and transports. It works in browsers and on servers, with conformance vectors for other languages.

@nonchalant/durable

Durable process support built from message and effect journals plus a six-method storage interface.

@nonchalant/host

A Node WebSocket host with origin checks, handshake authorization, per-connection scope, and connection limits.

03

The primitive

The API has two perspectives. Process is the handle used by callers, while Self is the interface available inside the generator.

From the outsideWhat it does
p()Reads the latest value synchronously. In a binding, effect, or derived value, it also subscribes to the paths that were read.
p.cast(msg)Sends a message without waiting for a response. It is available when the message type includes Cast messages.
p.call(msg)Sends a typed request and waits for its response. It is available for Call messages and rejects if the process crashes, finishes, or is disposed.
p.pending / p.stale / p.errorExposes lifecycle state through regular reads, using the same mechanism as application state.
for await (v of p)Iterates over current values. Slow consumers receive the newest value rather than a backlog.
p[Symbol.dispose]()Closes the mailbox, aborts the signal, runs finalizers, and disposes any owned child processes.
From the insideWhat it does
for await (msg of self)Reads queued messages in order. Handling is sequential by default, so repeated submissions wait instead of racing.
self.latest()Drops queued messages and returns the newest one, which is useful for inputs such as typeahead search.
self.signalAn AbortSignal triggered by disposal or a crash. Pass it to fetches and other cancellable work.
self.cast(msg)Sends a message to the process's own mailbox, allowing background work to report its result.

A one-way message is a Cast; a request that expects a response is a Call. TypeScript separates the two, so cast cannot accept a call and call cannot accept a cast.


type CartMsg =
  | Cast<{ type: 'add'; item: Item }>                             // a cast
  | Call<{ type: 'checkout' }, { ok: boolean; charged: number }>  // a call

cart.cast({ type: 'add', item })                 // fine
const res = await cart.call({ type: 'checkout' }) // res is typed; a crash rejects it

05

Why the updates stay small

State updates use standard immutable JavaScript. Each yielded value is compared structurally with the previous snapshot. A reader is notified only when the diff includes a path that it read.


s = { ...s, total: s.total + item.price }   // an ordinary immutable update
yield s                                     // diffed → only /total readers wake;
                                            // a binding on items[3].done sleeps through it

Dependencies are recorded automatically. While a binding runs, a temporary proxy tracks the paths it reads. This removes the need for dependency arrays and manual memoization. Views are created once, while keyed lists and replaceable regions handle structural changes.

06

Over the wire

lookup(name, args) can locate a shared dependency, a cached query, or a remote process. Transports provide send and subscribe over an ordered, reliable channel such as a socket, worker port, or tab-to-tab bus. Choosing where state runs changes one line:


const shop = registry({ cart: define(cart) })                        // this tab
const shop = connect<Shop>(portTransport(new Worker(url)))           // another thread
const shop = connect<Shop>(broadcastChannelTransport('shop'))        // another tab
const shop = connect<Shop>(webSocketTransport('wss://…'))            // another machine

The rest of the application uses the same process API in all four cases:

The same at every distanceWhy
The process itselfThe process has no transport-specific code. examples/shared-cart uses one definition in both the tab and Node host. examples/worker can move one definition across a thread boundary while it is running.
cast and callA cast uses one wire operation. A call pairs a request with its response. TypeScript preserves the distinction between them.
Targeted updatesA remote handle applies patches to a local process. A binding on /items/3/done is not notified when /total changes, regardless of where the source process runs.
Loading and failurepending, stale, and error are regular reads. If a host disconnects, the last value remains available and stale becomes true.
TeardownSymbol.dispose releases the subscription. The host can reclaim the process after its last subscriber leaves.

The wire carries patches made from plain data, not markup or executable code. Rendering and local interaction remain on the client, and payload size follows the size of the state change rather than the page. Other languages can implement a compatible host using the conformance vectors in packages/wire/spec/. After reconnecting, the client repeats its lookups and receives a full snapshot. That snapshot is compared with the retained value, so unchanged paths do not notify their readers.

Remote state comes with constraints. Values must be JSON-shaped; a Date or class instance is treated as an atomic value and cannot survive a remote lookup. Calls may fail or arrive late. The published schema limits which names are available, but it does not authenticate users. Authorization must be enforced by the host and the processes. In return, the application can share one implementation of its state across local and remote use.

Running the hosted demos. Start the chat room or shared cart with pnpm chat-server or pnpm cart-server, then open its page through pnpm dev. The shared cart can also keep its state in the tab; a commented line switches between local and hosted modes. Read Hosting safely before exposing a host to the internet. It covers origin checks, authorization, per-connection scope, and limits you must configure.

Two distributed examples need no server. Open multi-tab twice to see one tab become the host over a BroadcastChannel; another takes over when the host closes. The worker example can move the calculation between the main thread and a worker while it runs. Its results stay the same, while the frame meter shows the effect on responsiveness.

07

The same primitive on the server

The core package has no browser dependency. Its combination of a mailbox, generator, and supervision follows the actor model established by Erlang. The next three examples use processes for server state, durable state, and agent workflows.

A chat room on a server

The chat example starts with a simple process. A room adds posts to a limited history. It does not know about sockets, sessions, or the server that hosts it:


export const room: Proc<RoomState, RoomMsg, { name: string }> = async function* (self) {
  let lines: ChatLine[] = []
  let nextId = 1
  yield { lines }
  for await (const msg of self) {
    lines = [...lines.slice(-49), { id: nextId++, from: msg.from, text: msg.text }]
    yield { lines }
  }
}

The server registers the process, and browser tabs reach it through the same lookup API used locally. The name and arguments identify the room, so every lookup for the same room reaches the same process.


// the server
const host = await serve({ room: define(room, { evict: 3_600_000 }) }, { port: 4322 })

// a tab
const conn = connect<ChatSchema>(webSocketTransport('ws://127.0.0.1:4322/'))
const lobby = conn.lookup('room', { name: 'lobby' })   // get-or-spawn, on the server
Architecture: several tabs and one process per room 
flowchart LR
  T1["tab A"] -- "lookup room lobby" --> H
  T2["tab B"] -- "lookup room lobby" --> H
  T3["tab C"] -- "lookup room dev" --> H
  H["the host: one wire session per socket"] --> REG["registry: a name plus its args is the address"]
  REG --> P1[["room lobby"]]
  REG --> P2[["room dev"]]
  P1 -- "yield, diffed to a patch" --> H
  H -- "patch" --> T1
  H -- "patch" --> T2

The registry manages each room's lifetime. The first lookup starts it, later lookups share it, and the registry evicts it one hour after the last tab leaves. Suspended generators use little memory, allowing one Node process to host many rooms. If the server stops, tabs retain their latest snapshot with stale: true. Once the transport reconnects, a new lookup supplies a full snapshot.

Try it locally. Run pnpm chat-server, then open /examples/chat/ in several tabs. Before exposing a host to the internet, read Hosting safely for guidance on origins, authorization, connection scope, and resource limits.

State that survives a restart

Losing a chat room may be acceptable, but orders and long-running jobs must survive restarts. @nonchalant/durable records a process so it can recover. The wrapper returns a regular Proc, which can still be registered, accessed over a transport, and bound to a view.


const orders = registry({
  order: define(durable(order, { store, key: (args) => args.id })),
})

Each message forms a transaction boundary. The wrapper records the message before delivery and records every completed d.step effect. When the process requests another message, the new state and updated message cursor are committed together. If it crashes before that commit, recovery delivers the message again. The generator repeats its work, but completed effects are read from the journal instead of running again.

Architecture: what is recorded and when 
sequenceDiagram
  participant C as caller
  participant D as durable wrapper
  participant S as store (a port)
  participant P as your process
  C->>D: cast, or call with a callId
  D->>S: append(message)
  D->>P: deliver
  P->>D: step("charge")
  D->>S: putStep(result)
  P->>D: yield state
  P->>D: request the next message
  D->>S: commit(state, cursor) - together, or not at all
  Note over D,S: a crash before that commit delivers the message again
  Note over D,S: recorded steps answer from the journal instead of running

Calls also survive retries. A call includes an idempotency key, and the response is stored under that key. Retrying the call returns the stored response. d.call derives a stable key from the caller, current message, and call name, so replay uses the same key:


const receipt = await d.call('reserve', (callId) =>
  vault.call({ type: 'reserve', amount: 100, callId }))

This prevents a retry from repeating completed work. Calls with the same ID share one result, callers can recover a response after restarting, and a callee does not repeat a message after recording its answer.

Storage is defined by an eight-method port. It requires no base class or registration, and the durable wrapper does not depend on a particular database. This repository includes an in-memory adapter as the reference implementation and as the target of the crash-consistency tests. Production database adapters can live with the corresponding database drivers.

How durable execution is usually doneThe trade
Temporal replays workflow code against an event historyReplay is exact, but workflow code must remain deterministic and effects must run as activities.
DBOS and Restate journal individual steps in ordinary codeCode can remain conventional, but a step interrupted in progress may run more than once.
Nonchalant journals messages and steps, then commits the snapshot with its cursorRecovery loads one snapshot rather than replaying the full history. Recorded steps run once, while an effect interrupted before it was recorded may run again.

The package does not include worker fleet management, scheduling, cron, configurable retry policies, or an execution console. A mailbox has one writer only while a single node owns its name. If several hosts may activate the same ID, the storage layer needs a lease to coordinate them.

Messaging and queues

Backends often need pub/sub and work queues. The messaging demo defines both behind ports and provides in-memory adapters. A subscription can itself be a process: subscribe during setup, cast each event through self.cast, and unsubscribe when the process is disposed. This turns an external stream into state that views can read. Looking up the process by topic also lets the registry share one subscription among all readers of that topic.

A queue worker can also be modeled as a process: reserve a job under a lease, handle it, acknowledge success, and release it after failure. In the demo, press kill while a worker holds a job. Because the job is not acknowledged, its lease expires and another worker receives it with a higher attempts count. The queue provides at-least-once delivery, much as durable() does for messages inside a process.

Agent workflows

An agent receives a question, calls tools, examines their responses, and publishes progress. Those operations fit the same process API used by the earlier examples. The demo below combines the process from section 03 with the durable wrapper described above.

Agent stub model · ask about processes, patches, workers, or durability · try "refund 20"
source

Tools can be processes, reached with call(). Their state is observable; for example, the search tool tracks its call count. A registry lookup can reach the tool locally or through a transport.

Human approval uses the same request flow. Enter refund 20 in the demo. The approval tool holds the request until you choose a response. The agent waits with a normal await, while the approval queue is process state rendered by a regular view.


for await (const msg of self) {
  if (msg.type === 'request') waiting = [...waiting, { ...msg, reply: msg.reply }]  // parked
  else { waiting[0]?.reply(msg.ok); waiting = waiting.slice(1) }                    // a person decided
  yield state()
}

Press kill it while a question is running. The current process is disposed, and the next lookup starts a replacement that recovers from the journal without calling the model again.

Several agents

Common agent orchestration patterns can be written with the process API. In the multi-agent demo, a supervisor sends a brief to a researcher, passes the result to a writer, and requests approval before publishing.

The test suite exercises these workflows without a DOM or network. In examples/agent/agent.test.ts and examples/multi-agent/multi-agent.test.ts, the model is passed as an argument, tools run as processes, and yielded states form the execution record. Tests in packages/durable generate crash schedules and verify that recovered workflows reach the same state as uninterrupted runs.

Prior art it stands on

The propagation core is ported from alien-signals. Crank demonstrated generator components with local state. Erlang/OTP informed the mailboxes, casts, calls, and named processes. Cache keys, sharing, and idle eviction draw from TanStack Query. The targeted keyed diff follows ideas from Solid and lit-html. LiveView inspired server-owned state, though Nonchalant sends data patches instead of HTML.
